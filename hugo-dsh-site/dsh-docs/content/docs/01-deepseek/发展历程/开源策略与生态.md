## 为什么需要关心 DeepSeek 的开源策略？（痛点引入）

把 DeepSeek 接进 DSH 这类工具的人，迟早会被问到四个问题：权重能不能商用、能不能拿来蒸馏、开源周到底放了什么、为什么别人接模型比你便宜。这四个问题都不难，难的是**答案分散在不同的文件里，而且不同代际的答案不一样**。

- 法务问「权重能不能商用、能不能蒸馏出我们自己的小模型」，回答「开源了应该能用」——V2/V3 时代代码与权重是两份许可证（LICENSE-CODE 与 LICENSE-MODEL），混着答就会答错。
- 把 2025-02-24 那一周当成一次公关活动，只记住 FlashMLA 一个名字，漏掉了可以直接复用的 DeepGEMM 与 3FS。
- 以为「开源权重等于零成本自部署」，或者反过来以为「只有 API 一条路」，于是预算表里两种成本结构混着算。
- 引用时把 V4 系列写成「MIT 开源」——本次只核实到「开源权重 + 技术报告」，具体许可证文本未抓取，这一句就属于替官方升级了口径。

| 维度 | 没核对过开源策略时的代价 | 把许可证与开源周读清楚之后 |
|------|--------------------------|----------------------------|
| 商用合规 | 拿「开源」两个字当授权，法务复核时被打回 | 知道代码与权重可能各有一份文本，逐份核对 |
| 蒸馏与衍生 | 以为要单独谈授权，方案一拖再拖 | 知道 R1 起为纯 MIT，明确允许蒸馏等衍生 |
| 自部署选型 | 只盯参数量，忽略许可证与上下文 | 按「参数 + 上下文 + 许可证」三列一起选 |
| 基础设施复用 | 自己重写 MLA 解码与 MoE 通信 | 直接读 FlashMLA、DeepEP、DeepGEMM 的实现 |
| 成本估算 | 只算权重下载，不算算力与运维 | 分清 API 计费与自部署成本两条路 |
| 材料引用 | 把未核实的许可证写成已核实 | 未抓取的文本明确标注「未抓取」 |

> ### 💡 新人小结：DeepSeek 的开源到底开了什么？
>
> 把 DeepSeek 想象成一家「连菜谱带后厨图纸一起公开的餐馆」：
> - 早期只公开做法（代码 MIT），招牌酱料的配方另附一份使用协议（权重 Model License）——两样东西、两份合同。
> - 2025-01-20 起，连酱料配方也换成最宽松的 MIT——这就是「纯 MIT（代码 + 权重）」。
> - 2025-02-24 起的那一周，又把后厨设备图纸公开了：解码内核、通信库、矩阵乘库、流水线调度、文件系统。
>
> **开源策略回答的是「哪些东西你能拿走、拿走之后能做什么」，而不仅仅是「有没有放出权重」。**

**学习路线图**（本文按六段推进）

```
许可证演进 → 开源周六天 → 开源周之后 → 三层意义 → 与 harness 的关系 → 商用核对清单
能不能用     放了什么       还在放什么     影响谁      API 还是权重        落地前查什么
```

## 许可证演进：从双许可制到纯 MIT

先把四行事实摆出来，这张表逐行保留了源材料的阶段、许可证、覆盖范围与出处：

| 阶段 | 许可证 | 覆盖 | 出处 |
|------|--------|------|------|
| V2/V3 时代（含 LLM/Coder/VL 系列） | 双许可制：代码 MIT（LICENSE-CODE）+ 模型权重 Model License Agreement（LICENSE-MODEL） | 允许商用 | DeepSeek-V3 仓库 README License 节 |
| R1 起（2025-01-20） | 纯 MIT（代码 + 权重） | 明确允许蒸馏等衍生 | DeepSeek-R1 仓库 README License 节 |
| V3.2-Exp（2025-09-29） | MIT（含权重）确认 | 源材料未给出额外限制 | DeepSeek-V3.2-Exp 仓库 |
| V4 系列 | 开源权重 + 技术报告（HF collection deepseek-v4） | ⚠️ 具体许可证文本未抓取 | 官方新闻（2026-04-24） |

这张表有三处需要单独解释，否则很容易读偏：

1. **双许可制约束的是两个不同对象。** LICENSE-CODE 管代码，LICENSE-MODEL 管权重；表格里「允许商用」是两份文本共同给出的结论，不是任意一份单独给出的。这也解释了一个常见误判：代码是 MIT 不等于权重也是 MIT。
2. **R1 起切换为纯 MIT。** 代码与权重共用最宽松的那份协议，并且明确允许蒸馏等衍生（出处：DeepSeek-R1 仓库 README License 节）。对生态影响最大的一条就是它——蒸馏不必再逐案谈授权，这也是 R1 之后第三方蒸馏模型大量出现的前提。
3. **V4 系列的证据强度不同。** 本次只核实到「开源权重 + 技术报告」这一层，具体许可证文本 ⚠️ 未抓取。写材料时的正确口径是「开源权重」，而不是「MIT」。

同一件事，两种写法差别很大，下表是可直接照抄的对照：

| 要写的内容 | ❌ 容易写成的样子 | ✅ 有依据的写法 |
|------------|-------------------|------------------|
| V3 的权重授权 | 「V3 是 MIT 开源」 | 「V3 为双许可制：代码 MIT + 权重 Model License Agreement，允许商用」 |
| R1 的蒸馏 | 「蒸馏要看官方心情」 | 「R1 起代码与权重统一为纯 MIT，明确允许蒸馏等衍生」 |
| V4 的许可证 | 「V4 全系 MIT」 | 「V4 系列开源权重 + 技术报告；具体许可证文本未抓取」 |
| V3.2-Exp 的权重 | 「只开源了代码」 | 「V3.2-Exp 确认 MIT（含权重）」 |

> [!IMPORTANT] 引用纪律：许可证只认仓库里的 LICENSE 文件
> 本文的许可证结论全部来自官方仓库 README 的 License 节与对应 LICENSE 文件。二手转述、模型聚合站与博客里的「某模型已 MIT」都不算依据；写进合同或对外材料前，按仓库当前提交再核一次。

> ### 💡 新人小结：双许可制到底在管什么？
>
> 把一次开源想象成「买一套带装修的房子」：
> - 装修图纸（代码）走一份最简单的授权，谁都能改、能复用。
> - 房子本体（模型权重）另签一份合同，写了可以住、可以转租，但条款要逐条看。
> - 后来房东把两份合同合并成一份最宽松的（纯 MIT），从此住和改都不用再对照两份文件。
>
> **看到「开源」先问一句：开的是代码，还是权重，还是两个都开、各用哪份协议。**

## 开源周：2025-02-24 起连续 5+1 天

开源周（Open Source Week）从 2025-02-24 开始，连续 5+1 天放出训练与推理基础设施。下表逐日保留，一天都没有合并：

| 日 | 项目 | 内容 | 关键数字 |
|----|------|------|----------|
| Day 1（2025-02-24） | FlashMLA | Hopper GPU 高效 MLA 解码内核 | 3000 GB/s 内存受限、BF16 580 TFLOPS（H800） |
| Day 2 | DeepEP | 首个开源 MoE 专家并行通信库 | NVLink + RDMA、FP8 dispatch |
| Day 3 | DeepGEMM | FP8 GEMM 库（稠密 + MoE） | Hopper 上 1350+ TFLOPS，核心仅约 300 行 |
| Day 4 | DualPipe + EPLB + profile-data | 双向流水线并行 / 专家并行负载均衡 / 计算通信重叠分析 | 源材料未给出数字 |
| Day 5 | 3FS + smallpond | 萤火文件系统 + 数据框架 | 180 节点 6.6 TiB/s 聚合读；25 节点 GraySort 3.66 TiB/min |
| Day 6（One More Thing） | V3/R1 推理系统概览 | 推理系统披露 | 单 H800 节点 73.7k/14.8k 输入/输出 tokens/s，理论成本利润率 545% |

日期口径要说明一句：源材料只给了 Day 1 的日期（2025-02-24），Day 2 到 Day 6 没有逐日给出具体日期，因此表中其余各行不补日期，避免把「第几天」当成「几号」。

把六天连起来看，顺序本身就是一条推理链路：

```mermaid
flowchart LR
    D1["Day 1 FlashMLA 解码内核"] --> D2["Day 2 DeepEP 专家并行通信"]
    D2 --> D3["Day 3 DeepGEMM FP8 矩阵乘"]
    D3 --> D4["Day 4 DualPipe 与 EPLB 并行调度"]
    D4 --> D5["Day 5 3FS 与 smallpond 存储数据"]
    D5 --> D6["Day 6 V3 与 R1 推理系统概览"]
```

逐日看，每一天各自解决一个具体瓶颈：

1. **Day 1 FlashMLA 解决解码阶段的显存带宽瓶颈。** 解码是逐 token 生成的，瓶颈往往不在算力而在「搬数据」；3000 GB/s 内存受限、BF16 580 TFLOPS（H800）这组数字描述的就是这种受限状态下的吞吐水平。
2. **Day 2 DeepEP 解决 MoE 的专家并行通信。** 专家分散在不同卡上，一个 token 要按路由结果被送到对应专家，通信量随专家数上升；DeepEP 是首个开源的 MoE 专家并行通信库，支持 NVLink + RDMA 与 FP8 dispatch。
3. **Day 3 DeepGEMM 解决 FP8 矩阵乘的工程可用性。** Hopper 上 1350+ TFLOPS，核心仅约 300 行——行数少不是为了炫技，而是让人能在自己的集群上读懂并改。
4. **Day 4 解决「并行策略怎么排」与「负载怎么均衡」。** DualPipe 是双向流水线并行，EPLB 做专家并行负载均衡，profile-data 提供计算与通信重叠的分析数据；这一天的三个项目源材料没有给数字。
5. **Day 5 解决「数据怎么存、怎么批处理」。** 3FS 是萤火文件系统，smallpond 是数据框架；180 节点 6.6 TiB/s 聚合读、25 节点 GraySort 3.66 TiB/min 是这一天的两个规模指标。
6. **Day 6 不是新库，而是把前五天拼成一台整机。** V3/R1 推理系统概览给出了单 H800 节点 73.7k/14.8k 输入/输出 tokens/s，以及理论成本利润率 545%——注意这是「理论成本利润率」，不是财报口径的利润率。

> ### 💡 新人小结：为什么开源周要按顺序读？
>
> 把开源周想象成一次「后厨设备直播」：
> - Day 1 装的是出餐口（解码内核），决定单个 token 出得多快。
> - Day 2、Day 3 装的是传菜通道与灶台（通信库、矩阵乘库），决定多卡之间配合得好不好。
> - Day 4、Day 5 排的是工位顺序与仓库（流水线调度、文件系统），决定整条线不堵。
> - Day 6 是开业验收：把前五天的设备装成一台机器，报出每节点吞吐与理论成本利润率。
>
> **六天不是六个孤立项目，而是一台推理机器的零件清单加一张总装图。**

第三条的时间看起来「乱序」，原因是它按论文归属记录：这篇论文提交于 2024-08-26，比开源周早半年，被 open-infra-index 收进索引，用来解释萤火超算的软硬件协同设计。把它放在这里读，作用是给开源周的技术选择补一份「硬件底座说明书」——为什么 MLA 解码、MoE 通信、FP8 矩阵乘值得单独开源，答案在自家集群的形态里。

三件事的方向各不相同：

- **2025-04 的「推理引擎之路」**是经验型内容：把推理系统怎么搭、哪些环节吃资源讲出来，和 Day 6 的系统披露是同一主题的延伸。
- **2025-05 的 ISCA25 论文**是学术型内容：把 V3 的训练硬件与效率分析写成可引用的论文（arXiv:2505.09343）。
- **2024-08 的 SC'24 论文**是基础设施型内容：萤火二号的软硬件协同设计，arXiv:2408.14158，10,000 张 PCIe A100 的规格与配套软件栈都在里面。

公司的算力家底与这两篇论文的关系，见[公司历程与里程碑](/docs/01-deepseek/发展历程/公司历程与里程碑/)；本文只取「开源了什么」这一面。

## 三层意义：模型层、基础设施层、工具生态

开源周常被当成一条新闻读完，但它实际在三个层次上留下了可复用的东西：

| 层级 | 开源了什么 | 谁直接受益 | 可核实依据 |
|------|------------|------------|------------|
| 模型层 | R1 起 MIT 权重，允许蒸馏与商用衍生；官方另给 6 个 Qwen/Llama 蒸馏模型（1.5B–70B）作示范 | 做垂直模型、做私有化部署的团队 | DeepSeek-R1 仓库 README |
| 基础设施层 | MLA 解码、MoE 通信、FP8 GEMM、流水线并行、文件系统五件核心组件 | 自建训练/推理集群的工程团队 | open-infra-index |
| 工具生态层 | 低价 API + 开放权重，终端 Agent 工具与 harness 可低成本接入多种模型 | 做 Agent 工具与运行时的人 | 官方定价页 + 2025-09-29 降价公告 |

**模型层：许可证决定了「衍生」这件事的成本。** 双许可制时代，权重那份 Model License 允许商用，但衍生规则要逐条读；R1 起纯 MIT，蒸馏与商用衍生被明确允许。官方自己也给了示范：用 80 万蒸馏样本训练 6 个 Qwen/Llama 小模型（1.5B–70B）（出处：DeepSeek-R1 仓库 README）。示范的意义在于告诉生态「这条路走得通、长这样」，而不是只给一份法律文本。

**基础设施层：开源的是「效率方法」，不是「模型本身」。** FlashMLA、DeepEP、DeepGEMM、DualPipe/EPLB、3FS/smallpond 这五件东西，解决的是「同样的卡怎么跑出更高吞吐」。这层开源对同行最实用：模型权重能下载，但把权重跑得便宜的方法过去只写在论文里；开源周把它们变成了仓库。

**工具生态层：低价与开放权重是两件不同的事。** 低价 API 降低的是「试一个新模型」的成本，开放权重降低的是「把模型搬进自己机房」的成本。两者叠加，才有了 2025 年之后终端 Agent 工具密集出现的土壤：Codex CLI、Gemini CLI、Claude Code、OpenClaw 这类工具，以及 DSH 这类 profile 化运行时，都能用较低成本接入多种模型（出处：官方定价页与 2025-09-29 降价公告；工具侧情况见[终端编码代理浪潮](/docs/02-agent-tools/编码代理/终端编码代理浪潮/)）。

## 与 DSH 这类 harness 的关系：低价 API 加开放权重

先对齐一个词：**harness** 指把模型能力编排进实际工作流的运行时，DSH 属于其中「profile 化运行时」这一类——用配置描述「用哪个模型、走哪条链路」，而不是把模型焊死在代码里（DSH 的定位见[DSH 是什么](/docs/03-dsh/认识DSH/DSH是什么/)）。对这类软件，开源策略的影响落在两条接入路径上：

| 接入路径 | 成本结构 | 适合的场景 | 依赖的开源事实 |
|----------|----------|------------|----------------|
| 调 API | 按 token 计费，零运维、零显存 | 快速验证、流量波动大、不想养集群 | 低价 API：V3 定价、2025-09-29 降 50%+、当前峰谷计价 |
| 用开放权重自部署 | 自备算力与运维，单价与利用率强相关 | 数据不出机房、需要固定版本、长期高负载 | R1 起纯 MIT；V3.2-Exp 确认 MIT 含权重 |

价格这条线的三个节点，是「低价」这个词的依据：

| 时点 | 价格口径 | 出处 |
|------|----------|------|
| 2025-02-08 起 | V3：输入 cache miss $0.27/M、输入 cache hit $0.07/M、输出 $1.10/M | 官方新闻（2024-12-26 发布公告） |
| 2025-09-29 | V3.2-Exp 上线，API 价格下调 50%+ | 官方新闻（2025-09-29） |
| 2026-10（现行） | deepseek-flash 峰 $0.006/$0.3/$1.2（hit/miss-in/out，每 1M tokens），谷为峰半价；deepseek-v4-pro 峰 $0.044/$1.32/$3.96 | 官方定价页 |

把三行连起来读：从 $0.27 的 miss 输入价，到 deepseek-flash 的 $0.3，再叠加「谷为峰半价」，同一类请求的单价在两年里被压掉了不止一个数量级。这正是 harness 敢做「多模型路由」的前提——每多接一个模型，边际成本足够低；而开放权重则让同一套 harness 在私有化场景里能指向自部署端点。

> [!NOTE] 版本适用：价格必须带日期
> 上表三行分别对应 2025-02-08、2025-09-29 与 2026-10 三个时点，模型名也不同（V3、V3.2-Exp、deepseek-flash / deepseek-v4-pro）。把不同时点的单价放进同一张对比图之前，先确认要比较的是「同一类 token」还是「同一代模型」。

写接入决策时，建议把依据落成一条可复核的记录，而不是散在会议纪要里：

```yaml
# ========== 接入路径决策记录模板（字段口径来自本文引用的事实） ==========
provider: deepseek
access_path: api              # api 或 self_host，二选一，不写「都行」
api_model: deepseek-flash     # 2026-10 在售名，= V4.1-Flash-1017
context: 1M                   # 现行两个在售模型均为 1M
max_output: 384K              # 定价页口径
pricing_note: "峰谷计价，谷为峰半价；引用价格必须带日期"
weights_license: "R1 起纯 MIT；V3.2-Exp 确认 MIT 含权重"
evidence: "官方定价页 2026-10 + 2025-09-29 降价公告"
```

参数解释：

| 字段 | 含义 | 注意 |
|------|------|------|
| `access_path` | 走 API 还是自部署 | 二选一；「都行」等于没决策 |
| `api_model` | 在售模型名 | 只有 deepseek-flash 与 deepseek-v4-pro 两个（2026-10 口径） |
| `context` / `max_output` | 上下文与单次最大输出 | 两个在售模型均为 1M 与 384K |
| `weights_license` | 自部署时依据的许可证 | V2/V3 时代要分代码与权重两份，R1 起才是纯 MIT |
| `evidence` | 结论的出处 | 价格与许可证都要带日期或仓库提交 |

## 商用与蒸馏前的许可证核对清单

把上面所有内容压成一张可执行清单。清单的用法是：商用立项、蒸馏立项、对外发布衍生模型之前，逐行过一遍，每行都留下证据。

| 核对项 | 要查什么 | 通过标准 | 常见坑 |
|--------|----------|----------|--------|
| 代码授权 | 仓库里的 LICENSE-CODE | 是否为 MIT | 把代码 MIT 当成权重也 MIT |
| 权重授权 | 仓库里的 LICENSE-MODEL 或根目录 LICENSE | 是否允许商用、是否允许衍生 | 只看 README 的一句话总结 |
| 蒸馏许可 | 权重许可证中关于衍生模型的条款 | R1 起为纯 MIT，明确允许 | 拿 V3 时代的 Model License 套 R1 的结论 |
| 再分发 | 是否允许转发权重、是否要求附带协议 | 按许可证文本逐条核对 | 内网分发就默认不受约束 |
| 版本与日期 | 模型版本、仓库提交、抓取日期 | 三者齐全 | 只写模型名，不写版本 |
| 未核实项 | 许可证文本是否真的抓到 | 未抓取则标注「未抓取」 | 把「开源权重」写成「MIT」 |

配套的记录模板（照条目填，不写形容词）：

```text
# ========== 许可证核对记录（一个模型一条，结论必须能指到文件） ==========
model: DeepSeek-V3
code_license: LICENSE-CODE（MIT）
weights_license: LICENSE-MODEL（Model License Agreement）
commercial_use: 允许（两份文本分别适用）
distillation: 按 LICENSE-MODEL 条款逐条核对
redistribution: 按 LICENSE-MODEL 条款逐条核对
evidence: 仓库 README License 节 + LICENSE 文件，记录提交号与抓取日期

# ========== 同一模板用于 R1 时的差异 ==========
model: DeepSeek-R1
code_license: MIT
weights_license: MIT（与代码同一份协议）
distillation: 明确允许
evidence: DeepSeek-R1 仓库 README License 节
```

上表与模板的对应关系是：六行核对项分别落在模板的 `code_license`、`weights_license`、`distillation`、`redistribution`、`evidence` 与「未核实项」的处理方式上；模板里没有「大概可以」这种值。

> ### 💡 新人小结：核对清单为什么比「结论」更值钱？
>
> 把许可证核对想象成「出国前的证件检查」：
> - 护照（代码授权）和签证（权重授权）是两份文件，少一份都过不了关。
> - 目的地不同（商用、蒸馏、再分发），要看的条款也不同，不能拿上次的结论直接用。
> - 边检只认当下这一本，过期或版本不符就得重新办——所以记录里必须有版本与日期。
>
> **合规不是记住一句「它开源了」，而是每次都能拿出对应的文件与条款。**

## 常见误区自检（✅ 与 ❌ 对照）

| 场景 | ❌ 容易做错的判断 | ✅ 有依据的判断 |
|------|-------------------|------------------|
| 判断能否商用 | 「代码是 MIT，所以权重也能随便商用」 | 双许可制下代码与权重各一份文本，分别核对 |
| 判断能否蒸馏 | 「开源模型都不能蒸馏」 | R1 起纯 MIT，明确允许蒸馏等衍生 |
| 描述 V4 的授权 | 「V4 系列 MIT 开源」 | 「开源权重 + 技术报告」，具体许可证文本未抓取 |
| 看待开源周 | 「就是一次品牌活动」 | 六天分别对应解码、通信、矩阵乘、并行调度、存储、系统披露 |
| 引用开源周数字 | 把 545% 说成「利润率」 | 原文口径是「理论成本利润率」 |
| 估算自部署成本 | 只算权重下载 | 自部署要算算力、运维与利用率；API 按 token 计费 |

## 要点总结

1. **许可证是分层的**：V2/V3 时代代码走 MIT、权重走 Model License Agreement，允许商用但衍生规则要逐条读；R1（2025-01-20）起代码与权重统一为纯 MIT，明确允许蒸馏等衍生；V3.2-Exp 确认 MIT 含权重；V4 系列只核实到「开源权重 + 技术报告」。
2. **开源周是 5+1 天，不是五天**：Day 1 FlashMLA、Day 2 DeepEP、Day 3 DeepGEMM、Day 4 DualPipe + EPLB + profile-data、Day 5 3FS + smallpond、Day 6 V3/R1 推理系统概览；源材料只给了 Day 1 的日期 2025-02-24。
3. **开源周之后仍在开源**：2025-04 的推理引擎之路、2025-05 的 ISCA25 论文（arXiv:2505.09343），以及被索引收录的 SC'24 萤火论文（arXiv:2408.14158）。
4. **三层意义各管一段**：模型层给的是「能不能衍生」，基础设施层给的是「同样的卡怎么跑得更快」，工具生态层给的是「接一个模型有多便宜」。
5. **对 DSH 这类 harness，开源策略等于两条接入路径**：低价 API 让多模型路由的边际成本足够低，开放权重让私有化部署有合法依据；两条路各有自己的合规核对项。

---

> ### 💡 新人小结：开源策略与生态学完了，记住这 5 点
>
> 1. **先分清开的是代码还是权重**：两份文本、两套条款，R1 起才合成一份纯 MIT。
> 2. **「开源权重」不是「MIT」**：V4 系列目前只核实到开源权重与技术报告。
> 3. **开源周按零件读**：解码、通信、矩阵乘、并行调度、存储、系统披露，六天一条链。
> 4. **价格与许可证都要带日期**：2025-02-08 的 $0.27 与 2026-10 的 $0.3 不是一回事。
> 5. **合规靠清单不靠记忆**：商用、蒸馏、再分发三条路，各留一份能指到文件的记录。
